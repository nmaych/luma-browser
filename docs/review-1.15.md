# Luma Browser 1.15.0 全面测评与主流浏览器对比

测评对象：`release/1.15.0/win-unpacked/LumaBrowser.exe`（Electron 45.2.3 / Chromium 156 / Node 22）
对比基准：Chrome 157（本机实测）、Edge / Firefox / 搜狗 13.9（公开资料与实测目录结构）
测评方式：同一台机器、同一套 Playwright 注入测量启动与加载；内存取 `app.getAppMetrics()`；功能点逐项对照代码与实测。

## 一、结论摘要

| 维度 | 评分 | 一句话判断 |
| --- | --- | --- |
| 架构与工程质量 | B+ | 模块边界清晰、测试成体系；主进程仍有 2600 行的装配层 |
| 性能 | B− | 空载启动比 Chrome 慢约 0.3 秒；会话恢复急加载全部标签，内存与首屏都受影响 |
| 功能覆盖 | B | 日常浏览、广告拦截、阅读模式、PDF、会话恢复、截图、翻译都有；缺标签固定/分组、多配置档 |
| 安全 | B | 沙箱、CSP、fuses 都在；但 `--inspect` 未关闭、无代码签名、无证书钉扎 |
| 界面与交互 | A− | 视觉完成度高，深浅色与动效降级到位；缺键盘可达的标签检索 |
| 生态与扩展 | D | 无扩展、无同步、无多配置档，这是 Electron 的结构性限制 |

**总体判断**：作为个人项目，工程质量明显高于同规模 Electron 项目，界面接近商业产品水准。
真正的短板不在“写得好不好”，而在**产品完整性**：缺会话恢复、标签固定/分组这类“浏览器本来就该有”的能力，
以及扩展/同步这类需要长期投入的生态。下面按可执行性给出优先级。

## 二、实测数据

### 1. 启动（同一注入方式，3 次取样）

| 场景 | 到 UI 可交互 | 说明 |
| --- | --- | --- |
| Luma 空配置冷启动 | 1.42 / 1.46 / 1.52 s | 全新 profile，只有一个新标签页 |
| Luma 恢复 5 个标签 | 1.42 s 出界面，4 s 后仍有 2 个页面在加载 | 恢复的 5 个标签里创建了 4 个页面视图 |
| Chrome 157 冷启动 | 2.29 s | 首次运行 |
| Chrome 157 热启动 | 1.09–1.23 s | 新建空白标签 |

**结论**：空载启动 Luma 比 Chrome 热启动慢约 0.3 秒，差距不大；
但**会话恢复是"急加载"的**——重启后 5 个标签立刻建了 4 个页面视图，4 秒后仍有 2 个在加载，内存直接到 1.1 GB。
Chrome/Edge 只立即恢复当前标签，其余标签先显示标题占位，第一次点开才创建渲染进程。
这是启动体验里最值得改的一处，比"少读一个 JSON"收益大得多。

### 2. 内存（`app.getAppMetrics()` 工作集）

| 场景 | 进程数 | 合计 | 构成 |
| --- | --- | --- | --- |
| 1 个新标签页 | 4 | 404 MB | Browser 164 / GPU 81 / Utility 55 / Tab 104 |
| 10 个新标签页 | 5 | 558 MB | 同源标签共享渲染进程，增量很小 |
| 5 个真实站点 | 9 | 1340 MB | Tab 967 / Browser 191 / GPU 118 / Utility 64 |

说明：工作集把共享 DLL 重复计入，绝对值偏高；Chrome 任务管理器显示的是私有内存，两者不可直接比。
**可比的结论**：Electron 外壳的固定开销约 300 MB（Browser 164 + GPU 81 + Utility 55）。
Chrome 未用同一方式测量，因此不给出对比数字；页面内容部分同为 Chromium 156，量级应当一致。

### 3. 页面加载（回车 → 标签标题更新）

| 站点 | 耗时 |
| --- | --- |
| github.com | 370 ms |
| example.com | 530 ms |
| developer.mozilla.org | 630 ms |
| bing.com | 887 ms |

同网络下 Chrome 体感相当，差距在 100 ms 内，不构成体验问题。

### 4. 体积与依赖

| 项 | 数值 |
| --- | --- |
| 安装包 | 118.8 MB |
| 解压后目录 | 393 MB（Chrome 435 MB） |
| 运行时依赖 | 4 个（React、React DOM、lucide-react、Ghostery adblocker） |
| 代码量 | 主进程约 10.1k 行，渲染层约 12.1k 行 |
| 测试 | 61 项单测 + 44 项 Electron E2E + 5 项 Web E2E |

依赖面小是明显优点：无 lodash/moment 之类的“顺手引入”，升级 Electron 的风险可控。

## 四、做得好的地方

1. **标签的真实性**：每个标签是独立 `WebContentsView`，拖出/合并靠原生视图迁移，页面不刷新、播放不中断。
   这一点比很多“Electron 浏览器壳”强，后者用 `<webview>` 重载实现，体验差距明显。
2. **浮层不被网页遮挡**：菜单、地址栏建议、右键菜单用“镜像视图”盖在原生页之上，而不是截图占位。
3. **广告拦截是内置能力**：规则每周更新、可按站点暂停、盾牌显示拦截数，不依赖扩展生态。
4. **更新链路完整**：检查 → 后台下载 → 退出时静默安装 → 回滚包保留，接近搜狗 `QBDelayUpdate` 的做法。
5. **测试密度**：110 项自动化测试（61 单测 + 44 Electron E2E + 5 Web E2E）覆盖拖拽、截图、下载、书签、更新、数据迁移等真实路径，个人项目里少见。
6. **依赖克制**：4 个运行时依赖，攻击面与升级成本都低。
7. **会话恢复是自动的**：标签表持久化在 `localStorage`，重启后标题、顺序、活动标签都回来，不需要用户额外操作。

## 五、问题清单（按严重度）

测评过程中有两条初判被实测推翻，记在这里，避免把"看起来缺"当成"真的缺"：

- **PDF 查看**：初测用 DOM 查 `embed[type="application/pdf"]` 判定为空白页，改用 `capturePage()` 抓图后确认
  Chromium 内置查看器工作正常（缩略图、缩放、旋转、下载、打印齐全）。PDF 查看器跑在内部帧里，页面 DOM 查不到。
- **会话恢复**：代码里没有 `restoreSession` 之类的显式实现，但标签表持久化在 `localStorage`。
  实测关闭 3 个标签的窗口再启动，3 个标签连同标题全部恢复。

### P0 — 安全与分发

1. **打包版允许被附加调试器**：`electronFuses.enableNodeCliInspectArguments: true`，
   `LumaBrowser.exe --inspect` 仍能开调试端口。Electron 官方安全清单建议关闭，改一个布尔值即可。
2. **无代码签名**：SmartScreen 提示"未知发布者"，直接影响首次安装的信任与转化。
   个人开发者可用 Azure Trusted Signing 或 Certum 开源签名。

### P1 — 体验缺口，决定"能不能当主力"

3. **没有标签固定 / 标签组**：`pinned` 字段在整个代码库里都不存在。开 20+ 标签后标签栏只能横向滚动，
   常用的几个站无法钉住。这是当前与 Chrome/Edge/搜狗差距最明显的一项日常能力。
4. **标签栏缺键盘导航**：`role="tablist"` 有了，但没有 roving tabindex 与左右方向键切换。
   WAI-ARIA 的 tablist 模式要求方向键在标签间移动，纯键盘用户目前只能用 Ctrl+Tab 逐个循环。
5. **没有配置档（Profile）分离**：只有普通与无痕两套 `session`。工作/个人账号、不同登录态无法并存。
6. **会话恢复急加载**：实测重启恢复 5 个标签时，立刻创建 4 个页面视图、4 秒后仍有 2 个在加载，
   内存 1.1 GB。Chrome 只恢复当前标签，其余懒加载。这是启动体验最大的单点改善机会。
   次要因素：首屏要等设置、书签、历史、下载记录与广告引擎就绪，数据越多越慢（推断，未逐项拆分）。
7. **会话恢复没有策略选项**：恢复是"总是恢复"，没有 Chrome 的"启动时：打开主页 / 继续上次 / 打开指定页面"，
   也没有崩溃后的"恢复"提示条。

### P2 — 结构性限制，短期不建议投入

8. **扩展体系**：Electron 没有 `chrome.*` 扩展运行时，自建成本远超收益。
   可做"用户脚本白名单"覆盖一部分诉求。
9. **账号同步**：需要服务端与端到端加密，个人项目不建议自建；先做好书签/设置的导出导入。
10. **常驻更新服务**：Chrome 的 omaha 在应用不运行时也更新。当前要求应用运行，长期不开机会跳版本，
    可接受，但应在设置里说明。

## 六、改进建议（按投入产出排序）

| 优先级 | 事项 | 实现要点 | 成本 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | 关闭 `--inspect` | fuses 改 `false`，重新打包 | 10 分钟 | 带 `--inspect` 启动无调试端口 |
| 2 | 标签固定 | `pinned` 字段 + 图标化渲染 + 固定区置左 + 关闭行为调整 | 2 天 | E2E：固定后重启仍在、宽度收窄、拖动受限 |
| 3 | 标签栏键盘导航 | 单一 tabindex、左右键移动、Home/End、Enter 激活 | 1 天 | 键盘走查 + 可访问性断言 |
| 4 | 恢复标签懒加载 | 非活动标签只存元数据，首次激活再建 `WebContentsView` | 1–2 天 | 重启后页面视图数 = 1，内存回落 |
| 5 | 首屏分片加载 | 先渲染骨架，书签/历史/下载放到空闲回调 | 1–2 天 | 启动基准脚本对比前后 |
| 6 | 标签检索面板 | Ctrl+Shift+A，模糊匹配标题/URL，回车跳转 | 1.5 天 | E2E：输入关键字回车命中 |
| 7 | 启动策略设置 | 主页/继续上次/指定页面三选一，崩溃后给恢复提示 | 1 天 | E2E：切换策略后重启行为一致 |
| 8 | 代码签名 | Azure Trusted Signing 或 Certum | 取决于预算 | 安装包属性显示签名者 |
| 9 | 多配置档 | 独立 `session` 分区 + 头像切换 + 各自的书签/历史 | 3–5 天 | 两个配置档互不可见 Cookie |
| 10 | 用户脚本 | 仅 https、需用户确认、隔离世界执行 | 3 天 | 注入脚本无法触达 preload 上下文 |

## 七、不建议做的事

- **自研扩展商店/扩展 API**：Electron 没有 `chrome.*` 扩展运行时，复刻成本远超收益，
  且与“轻量浏览器”的定位冲突。
- **追求 Chrome 的进程模型细节**（如每个 iframe 独立进程）：收益小、稳定性风险大。
- **换 UI 框架重写**：现有界面完成度高，重写只会引入回归。

## 八、测评方法与局限

- 启动、加载耗时都包含 Playwright 注入开销（约 0.3–0.8 秒），只用于**同方法横向比较**，不代表双击启动的真实秒数。
- 内存为工作集求和，含共享页，绝对值偏高；跨浏览器比较请用各自任务管理器的私有内存。
- 功能对照以代码与实测为准；“搜狗/Edge”部分条目来自其安装目录结构与公开文档，未做逐项点击验证。
- 页面内渲染型能力（PDF 查看器、内置页面）不能用 DOM 判断，必须用 `webContents.capturePage()` 抓图复核——本次测评在这里纠正过一次误判。
