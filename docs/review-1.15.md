# Luma Browser 1.15.0 全面测评与主流浏览器对比

测评对象：`release/1.15.0/win-unpacked/LumaBrowser.exe`（Electron 45.2.3 / Chromium 156 / Node 22）
对比基准：Chrome 157（本机实测）、Edge / Firefox / 搜狗 13.9（公开资料与实测目录结构）
测评方式：同一台机器、同一套 Playwright 注入测量启动与加载；内存取 `app.getAppMetrics()`；功能点逐项对照代码与实测。

## 后续进展（1.17.0）

测评里的 P1 前三项已经落地，供对照：

| 建议 | 状态 | 结果 |
| --- | --- | --- |
| 关闭 `--inspect` | ✅ 1.17.0 | fuses 改为 `false` |
| 标签固定 | ✅ 1.17.0 | 右键固定到左侧、图标化、无关闭按钮、重启保留 |
| 会话恢复懒加载 | ✅ 1.17.0 | 4 标签重启：页面进程 3→1，内存 860→514 MB |
| 标签栏键盘导航 / 启动策略 / 多配置档 | 待做 | — |

## 一、结论摘要

| 维度 | 评分 | 一句话判断 |
| --- | --- | --- |
| 架构与工程质量 | B+ | 模块边界清晰、测试成体系；主进程仍有 2600 行的装配层 |
| 性能 | B− | 冷启动与 Chrome 持平，热启动慢 0.4–0.8 秒；内存底噪高约 100 MB |
| 功能覆盖 | B | 日常浏览、广告拦截、阅读模式、截图、翻译都有；缺会话恢复、PDF、标签固定/分组 |
| 安全 | B | 沙箱、CSP、fuses 都在；但 `--inspect` 未关闭、无代码签名、无证书钉扎 |
| 界面与交互 | A− | 视觉完成度高，深浅色与动效降级到位；缺键盘可达的标签检索 |
| 生态与扩展 | D | 无扩展、无同步、无多配置档，这是 Electron 的结构性限制 |

**总体判断**：作为个人项目，工程质量明显高于同规模 Electron 项目，界面接近商业产品水准。
真正的短板不在“写得好不好”，而在**产品完整性**：缺会话恢复、PDF 渲染这类“浏览器本来就该有”的能力，
以及扩展/同步这类需要长期投入的生态。下面按可执行性给出优先级。

## 二、实测数据

### 1. 启动（同一注入方式，3 次取样）

| 指标 | Luma 1.15（热启动） | Chrome 157（热启动） | 差距 |
| --- | --- | --- | --- |
| 进程就绪 | 1.22–1.82 s | 0.78–0.80 s | +0.5 s |
| 首个窗口 | 同左 | 1.09–1.17 s（新建标签） | +0.3 s |
| UI 可交互 | 1.64–2.83 s | 1.13–1.23 s | +0.4–1.6 s |

冷启动（全新 profile）：Luma 约 2.0–2.4 s 到可交互，Chrome 首次 2.3 s。
**结论**：冷启动基本持平，热启动慢在“主进程装配 + 首屏数据加载（设置、书签、历史、下载记录、广告规则）”。
数据量越大差距越明显，这也是最值得优化的一项。

### 2. 内存（`app.getAppMetrics()` 工作集）

| 场景 | 进程数 | 合计 | 构成 |
| --- | --- | --- | --- |
| 1 个新标签页 | 4 | 404 MB | Browser 164 / GPU 81 / Utility 55 / Tab 104 |
| 10 个新标签页 | 5 | 558 MB | 同源标签共享渲染进程，增量很小 |
| 5 个真实站点 | 9 | 1340 MB | Tab 967 / Browser 191 / GPU 118 / Utility 64 |

说明：工作集把共享 DLL 重复计入，绝对值偏高；Chrome 任务管理器显示的是私有内存，两者不可直接比。
**可比的结论**：Electron 外壳的固定开销约 300 MB（Browser+GPU+Utility），Chrome 同口径约 200 MB；
页面内容部分因同为 Chromium 156，量级一致。

### 3. 页面加载（回车 → 标签标题更新）

| 站点 | 耗时 |
| --- | --- |
| github.com | 370 ms |
| example.com | 530 ms |
| developer.mozilla.org | 630 ms |
| bing.com | 887 ms |

同网络下 Chrome 体感相当，差距在 100 ms 内，不构成体验问题。

### 4. 体积与依赖

| 项 | 数值 |
| --- | --- |
| 安装包 | 118.8 MB |
| 解压后目录 | 393 MB（Chrome 435 MB） |
| 运行时依赖 | 4 个（React、React DOM、lucide-react、Ghostery adblocker） |
| 代码量 | 主进程约 10.1k 行，渲染层约 12.1k 行 |
| 测试 | 61 项单测 + 44 项 Electron E2E + 5 项 Web E2E |

依赖面小是明显优点：无 lodash/moment 之类的“顺手引入”，升级 Electron 的风险可控。

## 四、做得好的地方

1. **标签的真实性**：每个标签是独立 `WebContentsView`，拖出/合并靠原生视图迁移，页面不刷新、播放不中断。
   这一点比很多“Electron 浏览器壳”强，后者用 `<webview>` 重载实现，体验差距明显。
2. **浮层不被网页遮挡**：菜单、地址栏建议、右键菜单用“镜像视图”盖在原生页之上，而不是截图占位。
3. **广告拦截是内置能力**：规则每周更新、可按站点暂停、盾牌显示拦截数，不依赖扩展生态。
4. **更新链路完整**：检查 → 后台下载 → 退出时静默安装 → 回滚包保留，接近搜狗 `QBDelayUpdate` 的做法。
5. **测试密度**：105 项自动化测试覆盖拖拽、截图、下载、书签、更新、迁移等真实路径，个人项目里少见。
6. **依赖克制**：4 个运行时依赖，攻击面与升级成本都低。

## 五、问题清单（按严重度）

### P0 — 正确性 / 安全，建议立刻修

1. **PDF 无法查看**（实测：打开 PDF 后 `body` 为空，没有 `application/pdf` 嵌入）。
   原因：页面视图的 `webPreferences` 没有开 `plugins`。Chrome/Edge/搜狗都能直接读 PDF，
   而下载 PDF 再找阅读器是明显的降级。
2. **打包版允许被附加调试器**：`electronFuses.enableNodeCliInspectArguments: true`。
   改一个字面量即可关闭，属于零成本的安全收益。
3. **无代码签名**：SmartScreen 提示“未知发布者”，直接影响首次安装转化。
   个人开发者可用 Azure Trusted Signing / Certum 开源签名，成本比商业 EV 证书低。

### P1 — 体验缺口，直接影响“能不能当主力”

4. **没有会话恢复**：关闭窗口后标签全部丢失，只有“恢复关闭的标签”。
   Chrome 用户的第一习惯是“下次打开还在”。实现路径：退出时把标签表写入
   `User Data/session.json`，启动时恢复（无痕窗口不写），配合“启动时：继续上次 / 打开主页”设置。
5. **没有标签固定 / 标签组**：长期开 20+ 标签的用户会很快感到拥挤。
   固定标签只需在数据模型加 `pinned` 字段 + 标签栏图标化渲染，是性价比最高的一项“主流功能”。
6. **启动耗时随数据量增长**：首屏要读设置、书签、历史、下载记录、广告规则五份数据。
   建议：窗口先显示骨架，数据在 `requestIdleCallback` 里补齐；广告引擎按 1.2 秒延迟加载（已有）可再提前到首帧后。
7. **无多配置档**：工作/个人分离是 Chrome 的高频能力，Electron 支持多 `session` 分区，改造成本中等。

### P2 — 长期方向 / 结构性限制

8. **扩展体系**：Electron 不支持 Chrome 扩展 API，自建扩展体系成本极高，不建议做；
   可考虑“内置增强”路线（脚本注入白名单、用户样式），覆盖 80% 的扩展诉求。
9. **同步**：需要服务端与端到端加密设计，个人项目不建议自建；可先做“书签/设置导出 + 手动导入”。
10. **常驻更新服务**：Chrome 的 omaha 在应用不运行时也更新。当前实现要求应用运行，
    对“一个月不开浏览器”的用户会跳版本。可接受，但应在设置里说明。

## 六、改进建议（按投入产出排序）

| 优先级 | 事项 | 实现要点 | 成本 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | 打开 PDF | `webPreferences.plugins = true`；保留“下载”入口 | 0.5 天 | E2E：打开 PDF 后检测 `embed[type="application/pdf"]` |
| 2 | 关闭 `--inspect` | fuses 改 `false` | 10 分钟 | 打包后 `--inspect` 无法附加 |
| 3 | 会话恢复 | `session.json` + 启动策略设置 + 崩溃后恢复 | 2–3 天 | E2E：写入标签→重启→标签数一致 |
| 4 | 标签固定 | `pinned` 字段、图标化、固定在左侧、Ctrl+W 行为调整 | 2 天 | E2E：固定后重启仍在、宽度收窄 |
| 5 | 首屏分片加载 | 骨架屏 + 空闲时读历史/下载/书签 | 1–2 天 | 启动基准脚本对比前后 |
| 6 | 标签检索面板 | Ctrl+Shift+A，模糊匹配标题/URL | 1.5 天 | E2E：输入关键字回车跳转 |
| 7 | 代码签名 | Azure Trusted Signing 或 Certum | 取决于预算 | 安装包属性显示签名者 |
| 8 | 多配置档 | 独立 `session` 分区 + 头像切换 | 3–5 天 | 两个配置档互不可见 Cookie |
| 9 | 生态替代 | 用户脚本白名单（仅 https、需确认） | 3 天 | 注入脚本在隔离世界执行 |

## 七、不建议做的事

- **自研扩展商店/扩展 API**：Electron 没有 `chrome.*` 扩展运行时，复刻成本远超收益，
  且与“轻量浏览器”的定位冲突。
- **追求 Chrome 的进程模型细节**（如每个 iframe 独立进程）：收益小、稳定性风险大。
- **换 UI 框架重写**：现有界面完成度高，重写只会引入回归。

## 八、测评方法与局限

- 启动、加载耗时都包含 Playwright 注入开销（约 0.3–0.8 秒），只用于**同方法横向比较**，不代表双击启动的真实秒数。
- 内存为工作集求和，含共享页，绝对值偏高；跨浏览器比较请用各自任务管理器的私有内存。
- 功能对照以代码与实测为准；“搜狗/Edge”部分条目来自其安装目录结构与公开文档，未做逐项点击验证。
